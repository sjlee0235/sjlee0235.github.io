# 플레이 데이터 수집 설계 (텔레메트리)

> 텔레메트리(telemetry) = 게임 안에서 일어난 일을 기록해 모으는 것.
> 목적: 시뮬레이션 봇이 아니라 **실제 사람이 어떻게 노는지**를 보고 밸런스를 맞추는 것.

이 문서는 "무엇을, 왜, 어떤 형태로 모으고, 모은 것을 어떻게 밸런스 조정으로 연결하는지"를 정리한다.
엔진 쪽 구조(이벤트 형식·기록·리플레이·분석 함수)는 이미 코드로 만들어 두었고(0단계), 화면·서버 쪽은 단계별 계획이다.

---

## 1. 핵심 아이디어: 가격은 기록하지 않고 "선택"만 기록한다

이 게임의 가격과 뉴스는 **시드(출발 숫자) + 엔진 버전 + 밸런스 설정**으로 100% 정해진다. 플레이어가 무엇을 사든 가격은 바뀌지 않는다.

그래서 기록은 두 가지만 있으면 된다.
1. **판의 조건**: 시드, 엔진 버전, 밸런스 지문(설정값 해시), 테마 추첨 결과
2. **플레이어의 선택**: 언제 무엇을 몇 주 사고팔았는지, 어떤 화면을 얼마나 봤는지

나머지(그 순간의 가격, 뉴스, 보유 평가액)는 **리플레이**(기록된 매매만 넣고 판을 다시 돌리기)로 언제든 다시 계산할 수 있다.

| 장점 | 설명 |
|---|---|
| 작다 | 2시간 시대 1판 ≈ 이벤트 200~300개, 44~87KB, 압축하면 **5~11KB** (봇 기준 실측) |
| 나중에 새 지표를 만들어도 된다 | 옛 기록을 리플레이해서 새 지표를 계산 |
| "만약에" 비교 | 같은 판에서 "이 사람이 그냥 들고만 있었다면?" → 매매 목록만 바꿔 리플레이 |
| 기록 검증 | 리플레이한 수익률 = 기록된 수익률인지 확인 (테스트로 보장) |

> 덧붙여, 이 성질을 세이브에도 썼다. 시대 중간 저장은 가격 대신 매매 기록을 저장하고, 불러올 때 리플레이로 되살린다 (README 5장 19번).

## 2. 전체 흐름

```
[엔진 Game] ──record()──▶ [TelemetrySink: 앱이 연결]
   │  자동 기록: 판 시작, 추첨, 뉴스 발표·반영,       │
   │  주가 리포트, 매매(+매매 순간 상황), 거부 주문,        ├─ 실제 시각(clientMs), 설치 id(pid), 판 id(gid) 덧붙임
   │  일시정지, 1분 자산, 정산                       ├─ 기기 저장 (최대 N개, 넘치면 오래된 것부터)
[화면 코드] ──game.track()──▶                      └─ (나중) 와이파이 연결 시 묶어서 업로드
   팝업을 몇 초 봤나, 어떤 화면을 열었나 등
                                   ▼
                     [분석: src/analytics/metrics.ts]
                     시대별 지표 · 뉴스별 지표 · 행동 유형 분류 · 이탈 지점
                                   ▼
               [밸런스 조정: src/engine/config.ts / 콘텐츠 수정]
                                   ▼
               balanceHash가 바뀜 → 패치 전후 기록을 나눠 비교
```

- 엔진은 저장·전송을 하지 않는다 (엔진 분리 원칙). `TelemetrySink`에 `record()`만 부른다. 연결하지 않으면 아무것도 기록하지 않고 게임 결과도 같다 (테스트로 확인).
- **기본은 꺼짐.** 기록 통(`TelemetrySink`)을 붙여도, 플레이어가 동의해 `setConsent(true)`가 되기 전에는 아무것도 내보내지 않는다. 판 도중에 동의하면 그 순간부터 기록하고, 그때까지의 행동(매매·입금)을 `game_start.priorActions`에 담아 리플레이할 수 있게 한다. 동의를 끄면 즉시 멈춘다. 동의 여부는 세이브(`telemetryConsent`)에 저장한다.
- 기본 구현 `TelemetryBuffer`: 메모리에 쌓고 `drain()`으로 꺼낸다. 넘치면 오래된 것부터 버리고 개수를 센다(게임이 느려지면 안 되므로).
- 형식은 **JSON Lines**(한 줄에 이벤트 하나). `toJsonLines` / `fromJsonLines`.

## 3. 이벤트 목록

### 공통 필드 (모든 이벤트)

| 필드 | 뜻 |
|---|---|
| `v` | 이벤트 형식 버전 (`TELEMETRY_SCHEMA_VERSION`) |
| `seq` | 게임 객체 안 일련번호 (빠진 기록·순서 확인) |
| `type` | 이벤트 이름 |
| `eraId`, `eraIndex`, `tick` | 어느 시대의 몇 번째 틱에 일어났나 |
| `clientMs` | (앱이 덧붙임) 실제 시각 |
| `pid`, `gid` | (앱이 덧붙임) 무작위 설치 id, 판 id. 개인 정보 아님 |
| (권장) `appVersion`, `platform`, `locale` | 앱이 업로드 묶음 머리에 한 번만 |

### 엔진 이벤트 (Game이 자동 기록) — 15종

| 이벤트 | 언제 | 주요 내용 | 왜 필요한가 |
|---|---|---|---|
| `game_start` | 기록 시작 (동의 직후, 또는 동의된 상태에서 Game 생성·세이브 이어 하기) | 모드(main/tutorial), 시드, 엔진 버전, 밸런스 지문, 시대 시작 자금, 기록 시작 틱·그 전 행동(`priorActions`), 지난 시대 수익률 | 리플레이의 출발점, 패치 버전 구분 |
| `era_start` | 시대 시작 | 추첨 시도 횟수, 활성 테마 20개, core 수, 쓸 수 있는 속보·스토리 수 | 추첨 조합에 따라 재미·수익이 갈리는지 |
| `news_published` | 뉴스 발표 | 뉴스 id, 종류, 스토리 id, 단서대로였나, 가상 여부, 규모, 영향 테마, **즉시 반영된 종목별 변동률** | 뉴스별 반응 분석의 기준점 |
| `news_reacted` | 5초 뒤 나머지 반영 | 종목별 변동률 (한도로 깎였으면 원래 값도) | 한도(±30%)가 얼마나 자주 걸리는지 |
| `report_created` | 발표 120초 뒤 | 주가 리포트에 나온 종목 (피드의 그 뉴스 아래에 붙음) | 리포트 열람률의 분모 |
| `trade` | 체결 | 매수/매도, 종목, 수량, 가격, 수수료, 남은 현금·수량, 실현손익, 보유 기간, 자동 청산 여부, **매매 순간 상황** | 모든 행동 분석의 중심 |
| `trade_rejected` | 거부된 주문 | 이유(잔고 부족 등) | 화면이 헷갈리게 만드는 곳 찾기 |
| `deposit` | 외부 유입 입금 | 금액, 출처(work/purchase/ad/other), 입금 뒤 현금, 시대 중인지 | 입금이 언제 들어오는지(큰 손실 직후?), 출처별 비중 |
| `favorite_toggled` | 관심 종목 토글 | 종목, 켬/끔 | 관심 종목 기능이 쓰이는지 |
| `paused` / `resumed` | 일시정지 / 재개 | 사유(`tutorial` / `background`) | 한 번에 얼마나 오래 하는지 (세션 길이) |
| `speed_changed` | 배속 변경 | 1 / 2 | 2배속을 얼마나 쓰나 (특히 파산 뒤, 작업 중) |
| `work_credit` | 인형 완성 (틱마다 묶음) | 완성 수, 적립 코인, 지급 방식 | 작업 수입 흐름, 리플레이 |
| `asset_snapshot` | 1분마다 | 현금, 평가액, 보유 종목 수 | 판 중 자산 곡선, 언제 무너지는지 |
| `era_end` | 시대 정산 | 최종 자산, 수익률(시간가중), 순손익(입금 제외), 출처별 입금, 매매 수, 수수료 합, 최고·최저 자산, 최대 낙폭, 보유 시간 비율, **작업 수입·작업 터치 수·상한으로 무시된 터치 수·완성 인형 수, 최종 코인, 파산 대기 시간(`brokeTimeSec`)** | 결과 분포, 작업이 투자를 압도하는지, 파산 뒤 할 일 없는 시간 |

### 매매 순간 상황 (`trade.context`)

"왜 이 타이밍에 이 종목을 샀나"를 나중에 추측하기 위한 값. 모두 매매 시점에 엔진이 이미 아는 값이다.

| 필드 | 뜻 | 쓰임 |
|---|---|---|
| `lastNewsId`, `ticksSinceNews` | 가장 최근 뉴스와 지난 틱 수. 0 = 발표 직후(즉시 몫만 반영), 1 = 나머지까지 반영 | 반응 속도 분포 → 즉시 반영 몫(75%) 조정 |
| `newsLink` | 이 종목 테마가 최근 뉴스에 어떻게 엮였나 (영향도, 강도) | 뉴스를 따라 사나, 반대로 사나, 강도 1(간접)까지 읽나 |
| `openStoryId`, `storyLink` | 진행 중인 스토리, 그 잠정 뉴스에서 이 테마의 영향도 | 단서를 읽고 미리 사는지 → 단서 확률(65%) 조정 |
| `eraChangePct`, `recentChangePct` | 시대 시작가 대비, 최근 1분 가격 변화 | 오른 것을 쫓아 사는지(추격 매수), 떨어진 것을 줍는지 |
| `assetsBefore` | 매매 직전 총자산 | 몰빵 정도 (매매 금액 ÷ 자산) |

### 앱(화면) 이벤트 — 화면 코드가 `game.track(type, data, clientMs)`로 기록 — 13종

| 이벤트 | 내용 | 왜 필요한가 |
|---|---|---|
| `app_session` | 시작/끝/백그라운드/복귀 | 세션 길이, 2시간 시대가 실제로 몇 번에 나눠 플레이되는지 |
| `tab_switch` | 어느 탭에서 어느 탭으로, 앞 탭에 머문 시간 | 탭별 체류 시간, 거실·작업실을 얼마나 쓰나 |
| `screen_view` | 화면·창(주문 패널, 정산, 돌아보기 등), 본 시간 | 어떤 창이 안 쓰이는지 |
| `feed_expand` | 접힌 뉴스를 펼침 (리포트 있었나) | 지난 뉴스·리포트를 다시 읽나 |
| `news_badge_click` | `NEWS!`를 눌러 주식창으로 | 알림이 행동을 바꾸나 |
| `max_button` | 주문 패널 '최대' (매수/매도, 수량) | 몰빵 정도, 버튼 쓰임 |
| `order_abandoned` | 주문 창을 열었다가 그냥 닫음 | 망설임 → 주문 화면 개선 |
| `lp_touch` | LP를 눌러 바뀐 장르 | 음악 기능 쓰임, 장르 선호 |
| `dog_touch` | 강아지 터치 (3번째마다 반응) | 거실 상호작용 쓰임 |
| `setting_changed` | 설정 변경 (언어, 색상, 볼륨 등) | 설정 사용률 |
| `tutorial_step` | 튜토리얼 단계 진입/건너뛰기/완료 (엔진이 단계 변화를 자동 기록) | 어느 단계에서 그만두나 |
| `client_error` | 오류 코드 | 안정성 |

- 시대별 **작업 터치 수**는 `era_end.workTouches`(엔진), **배속 변경**은 `speed_changed`(엔진)로 남는다.
- 이전 설계의 `news_popup`(뉴스 팝업)과 `related_theme_tap`(관련 테마)은 뉴스가 피드 행이 되고 방향 표시를 숨기면서 없앴다.

## 4. 지표 → 조정할 손잡이

모은 기록에서 이 지표들을 계산하고(`src/analytics/metrics.ts`), 목표에서 벗어나면 오른쪽 손잡이를 돌린다.
**한 번에 하나만** 바꾸고, 바꾸면 `balanceHash`가 바뀌므로 전후 기록을 나눠 비교한다.

| 지표 | 계산 | 건강한 모습(초안) | 벗어나면 돌릴 손잡이 |
|---|---|---|---|
| 시대 수익률 분포 | `era_end.returnPct`의 중앙값·하위/상위 10%·손해 본 판 비율 | 유형별로 시뮬레이션 목표표 안 | 영향도 1당 변동률, 배율, 수수료 |
| 반응 속도 | 뉴스 뒤 첫 매수까지 틱. 0틱 비율 | 0틱(5초 안) 매수가 소수 | `INSTANT_REACTION_SHARE`(즉시 반영 몫) |
| 초고속 반응 유형의 수익 | `newsSniper` 유형의 수익률 중앙값 | +30~80% | 즉시 반영 몫, 주문 지연 옵션 |
| 단서 읽기 유형의 수익·비율 | `storyReader` 수익률, 단서대로 나온 비율 | +25~100%, 단서 적중 ≈ 65% | `LEAN_PROB`, 잠정 뉴스 문장 |
| 분위기 보유 유형 | `holder` 중 긍정 테마 위주 보유자 수익 | +5~40% | 콘텐츠 분위기 편향(작성 가이드 75%) |
| 헷갈리는 뉴스 | 뉴스별 **방향 일치율**(호재에 매수·악재에 매도한 비율) | 강도 3 영향은 높아야 함 | 그 뉴스 본문·제목 수정, 연결 강도 재검토 |
| 안 읽히는 뉴스 | 주식창 체류 시간, `feed_expand` 비율 | 본문을 읽을 만한 시간 | 본문 길이, 피드 디자인 |
| 리포트 효과 | 리포트가 붙은 뒤 펼쳐 본 비율, 그 뒤 다음 뉴스 방향 일치율 변화 | 열람 후 일치율 상승 | 리포트 시점(120초), 리포트 문구 |
| 작업이 투자를 압도하나 | 시대별 `workIncome` ÷ 시작 자금, 작업 터치 수 분포 | 투자 수익보다 작게 (기획 판단) | `COINS_PER_DOLL`, `WORK_INCOME_CAP_PER_ERA` (`docs/economy.md`) |
| 파산 뒤 할 일 없는 시간 | `era_end.brokeTimeSec` 분포, 그동안의 2배속 사용 | 짧음 | 작업 수입 일부 선지급 같은 장치 (검토) |
| 탭 쓰임 | `tab_switch` 체류 시간, `lp_touch`·`dog_touch` 수 | 거실·작업실도 쓰임 | 화면 구성 |
| 이탈 지점 | 끝까지 안 한 판의 마지막 틱 분포, 세션 길이 | 특정 시점에 몰리지 않음 (특히 처음 7분 유예 구간) | 시대 길이(2시간), 7분 유예, 뉴스 간격, 이야기 구성 |
| 파산·의욕 상실 | 시대 2 시작 자금이 1,000코인 미만인 비율, 큰 손실 다음 판 이탈률 | 낮음 | 최소 자금 보조(검토 중, 6장 참고) |
| 추첨 운 | `era_start.coreCount`·스토리 수별 수익률 차이 | 차이가 작음 | 추첨 규칙(core 최소, 최소 속보·스토리) |
| 한도 걸림 | `news_reacted`에서 `requested`가 있는 비율 | 드묾 | 뉴스 사이 한도(±30%), 영향도 상한 |
| 거부 주문 | `trade_rejected` 이유별 빈도 | 드묾 | 주문 화면 (최대 수량 버튼 등) |
| 튜토리얼 | 단계별 진입 수 | 단계마다 큰 이탈 없음 | 튜토리얼 문구·길이 |

### 행동 유형 분류

`classify()`가 시대별 지표로 플레이어를 나눈다 (지금은 규칙 기반, 데이터가 쌓이면 군집 분석으로 바꾼다).

| 유형 | 판정 | 대응하는 봇 |
|---|---|---|
| `idle` | 매매 1회 이하 | — |
| `storyReader` | 매수 대부분이 잠정 뉴스 직후 + 잠정 뉴스 호재 쪽 | 잠정 정방향 |
| `storyContrarian` | 잠정 뉴스 직후 + 반대쪽 | 잠정 역방향 |
| `newsSniper` | 뉴스 반응률 50% 이상 + 반응 0틱 | 초고속 추종 |
| `newsFollower` | 뉴스 반응률 50% 이상 | 지연 추종 |
| `scalper` | 매매 100회 이상 | 무작위 매매 |
| `holder` | 보유 시간 70% 이상 + 매매 40회 이하 | 보유, 분위기 전략 |
| `mixed` | 그 밖 | — |

`npm run telemetry:report`를 실행하면 봇 기록으로 이 분류가 각 봇을 제대로 맞히는지 보여준다(테스트로도 확인).
실제 기록 파일은 `npm run telemetry:report -- 기록.jsonl`로 같은 표를 만든다. **사람과 봇을 같은 잣대로 비교**하는 것이 핵심이다.

### 사람 데이터로 시뮬레이션을 고치는 순환

1. 실제 기록에서 유형 비율과 유형별 행동 수치(반응 틱 분포, 몰빵 정도, 보유 시간)를 뽑는다.
2. 그 수치를 시뮬레이터 봇에 넣는다 (예: "반응 0틱 20%, 1~2틱 50%, 그 이상 30%"인 사람형 추종 봇).
3. 사람형 봇으로 밸런스 후보를 빠르게 시험한다 (`npm run sim:repeat -- 5 200 '{설정}'`).
4. 고른 후보를 소규모로 내보내고(가능하면 A/B: 그룹마다 다른 `balanceHash`), 실제 지표로 확인한다.

## 6. 개인정보·윤리 원칙

- **기본 꺼짐, 동의 후에만 수집.** 엔진은 `setConsent(true)` 전에는 기록을 내보내지 않는다 (테스트로 확인). 첫 실행 때 동의 화면에서 켜기/끄기를 고르고, 설정에서 언제든 바꿀 수 있다.
- **만 14세 이상 대상이어도 개인정보처리방침과 동의 화면이 필요하다.** 무엇을, 왜, 얼마나 오래 모으는지와 거부해도 게임 이용에 불이익이 없다는 점을 알린다. 출시 전 개인정보 보호 법령 기준으로 **전문가 검토**를 받는다 (이 문서는 법률 자문이 아니다).
- **개인을 식별할 수 있는 정보·기기 고유 ID는 기록에 넣지 않는다**: 이름·이메일·전화번호·위치·연락처, 광고 ID(IDFA/AAID), IMEI 등. 엔진 이벤트에는 이런 필드가 아예 없다 (테스트로 금지 필드 이름 검사).
- 플레이어 구분이 필요하면 앱이 처음 실행 때 만든 **무작위 설치 id**(`pid`)만 쓴다. 기기 정보에서 만들지 않고, 설정에서 초기화할 수 있게 한다. 기록 삭제 요청 방법과 보관 기간을 정한다.
- 기록은 밸런스·게임 개선과 운영 방식(광고를 넣을지, 어디에 넣을지 등) 결정에 **전체 통계로만** 쓰고, 개인을 겨냥한 광고·판매에 쓰지 않는다. (18차에 동의 문구에 '앞으로의 운영(광고 등)'과 '휴대폰 종류, 들어온 경로'를 넣었다.)
- 직접 만든 서버는 없다. 지인 테스트는 운영자 본인의 구글 스프레드시트로 받는다 (9장). 테스트가 끝나면 시트를 지우거나 보관 기간을 정해 안내한다.
- 아직 없는 것: 설정에서 설치 id 초기화, 기록 삭제 요청 창구. 정식 출시 전에 만든다.

## 7. 버전 관리 규칙

| 값 | 언제 올리나 |
|---|---|
| `TELEMETRY_SCHEMA_VERSION` | 이벤트 필드의 뜻이 바뀌거나 필드가 빠질 때 (추가만이면 그대로 둬도 됨). 현재 3 (2: `priorActions`·`deposit`, 3: `report_created`, `paused{reason}`, `speed_changed`, `work_credit`, `era_end`의 작업·파산 필드, 탭 기준 앱 이벤트) |

| `balanceHash` | 자동 (설정값이 하나라도 바뀌면 달라짐) |

엔진 규칙을 고친 커밋에서는 `ENGINE_VERSION`을 올렸는지 확인한다.

## 9. 지인 테스트 수집 세팅 (18차)

### 흐름

```
[지인 휴대폰: GitHub Pages 게임] ── 동의한 사람만 ──▶ [내 구글 스프레드시트 'events' 탭]
   기기 큐에 모았다가 20초마다·화면을 떠날 때 묶어서 보냄        한 줄 = 이벤트 하나
   (주소가 아직 없거나 인터넷이 끊기면 기기에 두었다가 다음에)         ▼
                                              [파일 → 다운로드 → CSV] → npm run playtest:report
```

- 보내는 곳은 **GitHub Pages 주소에서만** (개발 서버·`?debug=1`·아티팩트 미리보기에서는 보내지 않음).
- 줄마다 붙는 구분자: `pid`(이 브라우저에서 처음 열 때 만든 무작위 문자열), `sid`(이번 접속), `gid`(판 = 시드), `build`(배포 이름, 지금 '18차'), `clientMs`(실제 시각).
- 접속할 때 한 번 `session_begin`: 유입(주소의 `?src=` / `utm_source`, 없으면 인스타·카톡 등 앱 안 브라우저로 추정), 운영체제·브라우저 종류, 휴대폰 여부, 화면 크기(20 단위로 뭉갬), 언어, 시차, 몇 번째 접속인지, 처음 연 날로부터 며칠째인지. 브라우저 전체 문자열(UA)·IP·기기 번호는 담지 않는다.
- 엔딩 화면을 보면 `ending_view`(엔딩, 최종 코인, 누적 수익률, 마지막 단계, 작업 수입).
- 인스타그램 게시물·스토리마다 주소 끝에 `?src=이름`을 붙이면 어디서 많이 들어왔는지 나눠 볼 수 있다 (예: `…/invest-rpg/play/?src=story1`).

### 받는 곳 만들기 (운영자가 한 번, 약 5분)

1. 구글 드라이브에서 **새 스프레드시트**를 만들고 이름을 정한다 (예: 역전의 방 플레이 기록).
2. 메뉴 **[확장 프로그램] → [Apps Script]**.
3. 원래 있던 코드를 모두 지우고 `tools/telemetry_apps_script.gs` 내용을 통째로 붙여 넣은 뒤 저장(디스크 아이콘).
4. 오른쪽 위 **[배포] → [새 배포]** → 톱니바퀴에서 유형 **'웹 앱'** → 실행 계정 **'나'**, 액세스 권한 **'모든 사용자'** → **[배포]**.
5. 권한 요청이 뜨면 내 계정 선택 → "확인되지 않은 앱" 화면이면 **[고급] → [(프로젝트 이름)(으)로 이동] → [허용]** (내가 만든 코드가 내 시트에 쓰는 권한).
6. 나온 **웹 앱 URL**(`https://script.google.com/macros/s/…/exec`)을 복사해 개발 쪽에 전달 → `src/ui/telemetryConfig.ts`의 `TELEMETRY_ENDPOINT`에 넣고 다시 배포한다.
7. 확인: 그 URL을 브라우저로 열면 "역전의 방 플레이 기록을 받는 중이에요. 쌓인 줄 수: N"이 보인다.

(선택) 분석을 맡길 때 시트를 직접 내려받지 않으려면: Apps Script [프로젝트 설정] → [스크립트 속성]에 `EXPORT_KEY` = 아무 비밀 문자열 → `웹 앱 URL?key=그 문자열`로 전체 기록을 JSON으로 받을 수 있다. 이 문자열은 공개하지 않는다.

주의: 웹 앱 URL은 게임 코드 안에 들어가 누구나 볼 수 있다. 장난으로 가짜 줄을 보낼 수는 있으니(읽기는 못 함), 이상한 줄이 보이면 pid별로 걸러 본다. 코드를 고쳐 다시 배포할 때는 [배포] → [배포 관리] → 연필 → 버전 '새 버전'으로 하면 URL이 그대로다.

## 10. 무엇을 보려고 모으나 — 질문 → 기록 → 지표 → 바꿀 것

보고서(`npm run playtest:report`)의 각 줄은 아래 질문에 답한다. 지인 테스트는 사람 수가 적으니(수십 명) 숫자 하나보다 **방향**을 본다.

### 난이도

| 질문 | 기록 | 지표 | 이러면 이렇게 바꾼다 |
|---|---|---|---|
| 끝까지 가나? | `game_start` · `era_end`(시대별) · `ending_view` | 진행 단계별 남은 판 수 | 첫 시대에서 많이 멈춤 → 첫 시대를 짧게·쉽게, 튜토리얼 보강 |
| 어디서 그만두나? | 엔딩 전 판의 마지막 기록 (시대·10분 단위) | 멈춘 곳 분포 | 특정 구간에 몰림 → 그 구간의 뉴스 간격·지루함 점검 |
| 너무 쉽나/어렵나? | `era_end.returnPct`·`maxDrawdownPct` | 시대별 수익률 중앙값, 플러스 비율 | 플러스 비율 90%↑ = 너무 쉬움 / 40%↓ = 너무 어려움 → 반영 비율·뉴스 크기(`config.ts`) |
| 엔딩 비율은? | `ending_view.ending` | 새드·중립·해피 비율 | 해피가 거의 없음 → 인테리어 값·작업 보상 조정 |
| 어떻게 노나? | `trade` + 매매 순간 상황 | 유형(뉴스 저격·단서 읽기·장기 보유 …) | 한 가지 유형만 이기면 그 전략의 이득을 줄인다 |
| 돈이 묶여 손을 놓나? | `era_end.brokeTimeSec` | 파산 대기 시간 > 0 비율 | 높음 → 작업 보상 올리기, 최소 자금 장치 |
| 화면이 헷갈리나? | `trade_rejected` · `order_abandoned` · `client_error` | 거부 사유·망설임 횟수·오류 | 많은 화면부터 고친다 |

### 사업 모델 (광고·구매를 붙인다면)

광고 SDK는 넣지 않았다 (CLAUDE.md 규칙). 아래는 **나중에 붙인다면 어디가 자연스러운지**를 지금 플레이로 미리 가늠하는 지표다.

| 질문 | 기록 | 지표 | 쓰임 |
|---|---|---|---|
| 얼마나 자주·오래 오나? | `session_begin`(몇 번째 접속, 며칠째) · 기록 시각 | 재방문 비율, 다음 날 이후 다시 온 비율, 접속 1번 길이 | 광고 노출 가능 횟수 추정. 재방문이 낮으면 광고보다 재미·알림이 먼저 |
| 시대 사이에 쉬어 가나? | `screen_view(settlement)` dwell · `era_end` 횟수 | 정산 화면 머문 시간, 시대 끝 횟수 | 전면 광고 후보 지점 (게임 흐름을 끊지 않는 곳) |
| 코인이 아쉬운 순간이 있나? | `interior_insufficient` · `brokeTimeSec` | "코인 부족" 시도 수·사람 수 | 보상형 광고("광고 보고 코인 받기")·코인 구매 수요 |
| 시간을 아끼고 싶어 하나? | `speed_changed(2)` | 2배속을 쓴 사람 비율 | "시간 건너뛰기" 보상·유료 배속 수요 |
| 작업(터치) 수입이 큰가? | `era_end.workIncome` vs `profitAmount` | 작업 비중 | 크면 "광고 보고 작업 보상 2배" 후보 |
| 꾸미기·강아지에 관심 있나? | `interior_upgrade` · `dog_touch` · `lp_touch` | 횟수·사람 수 | 꾸미기 아이템(구매) 수요 |
| 어디서 들어왔나? | `session_begin.source/inApp` · `?src=` | 유입별 사람 수·끝까지 간 비율 | 홍보 채널 비교 (인스타 스토리 vs 게시물 vs 카톡) |

### 지금 모으지 않는 것 (일부러)

- 이름·연락처·이메일·IP·기기 고유 번호·광고 ID·정확한 위치·브라우저 전체 문자열.
- "광고를 보겠냐"는 가짜 버튼 (기획에 없는 기능이라 넣지 않았다. 원하면 설문 화면을 따로 기획한다).
